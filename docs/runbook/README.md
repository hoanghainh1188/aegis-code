# Operations Runbook: aegis-server (AWS)

For operators running Aegis on AWS (#33, [ADR 0003](../adr/0003-platform-service-architecture.md) §6). For self-hosted on-premise deployments without AWS, see [on-premise.md](on-premise.md). Four common tasks: [Deployment](#1-deployment), [Rollback](#2-rollback), [Secret Rotation](#3-secret-rotation), [Troubleshooting](#4-troubleshooting), [Adding Repositories](#6-adding-repositories). Metrics, alerts, and Grafana: [Monitoring](#5-monitoring). The [Account Setup](#0-account-setup) section is performed only once per account.

## Overview

| Component | Location |
| --- | --- |
| `aegis-server` Image (includes `aegis-aci`, `codebase-memory-mcp`, `git`, `docker` client) | [docker/server/Dockerfile](../../docker/server/Dockerfile), ECR `aegis-server:<commit-SHA>` |
| Profile Sandbox Images | `docker/<profile>/`, ECR `aegis-sandbox-<profile>:<SHA>`, tagged locally as `aegis-sandbox-<profile>` |
| Infrastructure | [deploy/tofu/](../../deploy/tofu/): module `modules/aegis`, environments `envs/staging`, `envs/customer-jp`, one-time setup in `bootstrap` |
| CI/CD | [.github/workflows/deploy.yml](../../.github/workflows/deploy.yml) |
| Host Machine | Single EC2 (Amazon Linux 2023) running `aegis` container with `all` role via systemd unit `aegis.service`; behind ALB with TLS |
| Server Configuration | `/etc/aegis/server.toml` on host, generated by OpenTofu from [server.toml.tftpl](../../deploy/tofu/modules/aegis/server.toml.tftpl). Contains no secrets |
| Secrets | AWS Secrets Manager, named `aegis/<environment>/<NAME>`; OpenTofu provisions placeholders, values set by operators |
| Active Image Tag | SSM parameter `/aegis/<environment>/image_tag` |
| Logs | CloudWatch Logs `/aegis/<environment>/server` (same AWS region) |
| Job Workspace, Build Cache, Docker Images | Dedicated EBS volume mounted at `/data`; workspace bound to `/srv/aegis/.workspace` |
| Monitoring | Second EC2 instance `aegis-<environment>-monitoring`: Prometheus, Alertmanager, Grafana; alerts routed via SNS `aegis-<environment>-alerts`. See [5. Monitoring](#5-monitoring) |

**customer-jp:** All components above (EC2, RDS, EBS, secrets, logs, ECR, state) reside strictly in `ap-northeast-1` (Tokyo). The region is hardcoded in `envs/customer-jp` and verified by the module; server refuses startup under `customer_jp` mode if the secret store is not located in `ap-northeast-1`.

### Worker and Docker Isolation

The gate executes each verification step inside a sandbox container (`docker run --network none --cap-drop ALL …`, Architecture §6–§7). On EC2, the `aegis` container communicates with the **host Docker daemon** via the mounted socket `/var/run/docker.sock`, with `--group-add` matching the socket group (container user is uid 10001, non-root). Sandboxes are sibling containers to `aegis`, not nested containers.

Two key implications:

- **Workspace path parity:** The workspace path must be identical inside the container and on the host (`/srv/aegis/.workspace`), because the gate sends its own paths to the Docker daemon when mounting `/work`. The sandbox executes as uid 10001, so this directory must be owned by uid 10001.
- **Security boundary:** Controlling the Docker socket grants effective root access to the host machine. A command injection vulnerability in the gate's `docker run` parameters (e.g., mounting `/`) could compromise the host and its IAM instance profile. Current mitigations: the gate constructs arguments as an array without passing through shell parsing; the EC2 instance runs only Aegis; IMDSv2 hop limit is set to 1 so bridge/none network containers (sandboxes, Sonar scanners) cannot retrieve host metadata credentials, while `aegis` runs with `--network host` to access IMDS; instance IAM role is scoped strictly to reading `aegis/<environment>/*` secrets, pulling ECR, and writing CloudWatch logs; SSH is disabled. Future hardening: rootless Docker, socket filtering proxy, or separating worker instances from API nodes.

## 0. Account Setup

Performed once per AWS account using temporary administrator credentials (SSO), without creating long-lived IAM access keys. If `staging` and `customer-jp` share an account in `ap-northeast-1`, this runs once; if using separate accounts, repeat for the second account and configure variables per GitHub environment.

1. **State Bucket** (versioning enabled, encrypted, public access blocked):

   ```bash
   B=aegis-tofu-state-<account-id>
   aws s3api create-bucket --bucket $B --region ap-northeast-1 --create-bucket-configuration LocationConstraint=ap-northeast-1
   aws s3api put-bucket-versioning --bucket $B --versioning-configuration Status=Enabled
   aws s3api put-bucket-encryption --bucket $B --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
   aws s3api put-public-access-block --bucket $B --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
   ```

   State locking uses a `.tflock` file directly in this bucket (`use_lockfile`), requiring no DynamoDB table.

2. **OIDC, CI Roles, ECR:** In `deploy/tofu/bootstrap`, copy `backend.hcl.example` to `backend.hcl`, create `bootstrap.tfvars` (see `example.tfvars`), then run:

   ```bash
   tofu init -backend-config=backend.hcl
   tofu apply -var-file=bootstrap.tfvars
   ```

   This provisions three IAM roles: `aegis-ci-plan` (PR and main, read-only), `aegis-ci-image` (main, pushes to ECR), and `aegis-ci-apply` (scoped to GitHub environment jobs; cannot read or write secret values).

3. **GitHub Configuration** (Settings → Secrets and variables → Actions → Variables; no AWS access secrets stored in GitHub):
   - Repository variables: `AWS_PLAN_ROLE_ARN`, `AWS_IMAGE_ROLE_ARN`, `TF_STATE_BUCKET`, `TOFU_TFVARS_STAGING`, `TOFU_TFVARS_CUSTOMER_JP` (HCL content as in `envs/<env>/example.tfvars` with real values).
   - Environments `staging` and `customer-jp`: *Required reviewers*, *Deployment branches* set strictly to `main`, variable `AWS_APPLY_ROLE_ARN`.

4. **Initial Images:** Merge to `main` (or re-run workflow on main) so that jobs `image` and `sandbox-images` push `<SHA>` tags to ECR.

5. **Infrastructure Provisioning:** Actions → Deploy → Run workflow: `environment=staging`, `action=apply`. Review the execution plan under job `plan`, approve job `apply`. The EC2 host is provisioned but server has not started yet (tag `bootstrap`).

6. **DNS:** If `route53_zone_id` is supplied, DNS records are configured automatically. Otherwise, retrieve output values `certificate_validation_records` and `alb_dns_name` (`tofu output` in `envs/<env>`), and create validation CNAME records plus `domain_name` → ALB CNAME at your DNS provider. The HTTPS listener requires an issued certificate, so re-run `apply` once DNS validation succeeds.

7. **Database User & Secrets:** See [3. Secret Rotation](#3-secret-rotation) for setting secret values. On initial setup, create the `aegis` application database role (the server does not use the RDS master user, as RDS automatically rotates the master password):

   ```bash
   # On operator machine: forward RDS connection through aegis EC2 via SSM (no SSH required)
   aws ssm start-session --target <instance_id> --document-name AWS-StartPortForwardingSessionToRemoteHost \
     --parameters host=<db host>,portNumber=5432,localPortNumber=15432
   # In another terminal: retrieve RDS master password (output db_master_secret_arn)
   aws secretsmanager get-secret-value --secret-id <db_master_secret_arn> --query SecretString --output text
   PW=$(openssl rand -hex 24)
   psql "postgres://aegis_admin@localhost:15432/aegis?sslmode=require" \
     -v pw="$PW" -c "CREATE ROLE aegis LOGIN PASSWORD :'pw'" -c "GRANT aegis TO aegis_admin" -c "ALTER DATABASE aegis OWNER TO aegis"
   aws secretsmanager put-secret-value --secret-id aegis/staging/AEGIS_DATABASE_URL \
     --secret-string "postgres://aegis:$PW@<db host>:5432/aegis?sslmode=require"
   unset PW
   ```

8. **Initial Launch:** Perform [1. Deployment](#1-deployment) using the newly built commit tag. Database migrations run automatically during server bootstrap.

9. **Initial RBAC Setup:** Access the host via `aws ssm start-session --target <instance_id>`, then execute:
   ```bash
   sudo docker exec aegis aegis-server --config /etc/aegis/server.toml grant <email> admin
   ```
   For service tokens: `... token <service_name>` (reference: [auth/cli.rs](../../crates/aegis-server/src/auth/cli.rs)).

10. **Onboard First Repository:** Follow [6. Adding Repositories](#6-adding-repositories).

## 1. Deployment

Every commit merged into `main` builds container images `aegis-server:<SHA>` and `aegis-sandbox-<profile>:<SHA>` on ECR (immutable tags).

1. Verify new migrations follow the expand/contract guidelines below. Review migration behavior in staging first.
2. Actions → Deploy → Run workflow: specify `environment`, `action=deploy`, `image_tag=<SHA>`. Approve deployment job.
3. The workflow validates the image on ECR, writes the tag to `/aegis/<env>/image_tag`, and triggers `aegis-deploy <SHA>` on the EC2 host via AWS SSM. The script pulls the server and sandbox images, restarts systemd unit `systemctl restart aegis`, and waits for `/api/v1/health` to return HTTP 200 (timeout: 5 minutes). The workflow job summary records the **previous tag** for instant rollback.
4. Restart terminates the old container using `SIGTERM`: the HTTP API ceases accepting new requests, while workers stop leasing new jobs and wait for in-flight tasks up to `worker.drain_s` (default 600 s; `docker stop` timeout provides an extra 60 s). Incomplete jobs are safely returned to the queue for subsequent worker execution. To prevent job interruption, schedule deployments during low activity periods (monitored via Grafana dashboard).
5. Rollout order: deploy staging first, execute an evaluation issue, then deploy to customer-jp with the identical image tag.

> [!WARNING]
> **EC2 Instance Replacement:** Modifying infrastructure parameters in `deploy/tofu` (e.g. `instance_type`, `user_data`, or base AMI) may trigger a full instance replacement (`must be replaced` in Tofu plan). While workspace data and container layers reside on the separate EBS volume (`/data`) and persist, any in-flight jobs will be abruptly cut off. **Best Practice:** Prior to applying replacement plans, switch the unit to `--role api` and wait for `worker.drain_s` so active jobs conclude cleanly.

### Database Migrations: Expand/Contract Pattern

Rollback procedures revert container images without rolling back the database schema. Therefore, all migrations must maintain bidirectional compatibility across consecutive releases:

- **Expand Phase** (Release N): Add new tables, nullable columns, or columns with defaults; create indices (`CONCURRENTLY` for large tables). New application code writes to both old and new columns when necessary.
- **Contract Phase** (Release N+1 or later, after rollback to pre-expand releases is no longer needed): Remove deprecated columns/tables, enforce `NOT NULL` constraints.
- Never rename or alter column types in a single step; never drop entities still referenced by the previous version.
- Aegis server automatically skips already applied migrations that are unfamiliar to its current binary (#176). Consequently, an older binary safely boots against a database migrated by a newer expand release. Modifying an existing migration checksum causes startup termination with `VersionMismatch`. Never alter an already released migration; author a new migration file instead. Never manually delete rows from `_sqlx_migrations`.

## 2. Rollback

If a newly deployed release fails (health check fails, error spikes in logs, incorrect behavior):

1. **Identify Previous Tag:** Check the job summary from the latest deploy workflow run, or query SSM parameter history:
   ```bash
   aws ssm get-parameter-history --name /aegis/<env>/image_tag --query 'Parameters[].[LastModifiedDate,Value]' --output text
   ```
2. **Execute Rollback:** Actions → Deploy: set `action=deploy`, `image_tag=<previous-tag>`.
3. **Emergency Fallback (GitHub Actions unavailable):** Open host session via `aws ssm start-session --target <instance_id>`, then execute:
   ```bash
   sudo /usr/local/bin/aegis-deploy <previous-tag>
   aws ssm put-parameter --name /aegis/<env>/image_tag --value <previous-tag> --overwrite
   ```
4. **Data Integrity:** The database schema is not rolled back (guaranteed by expand/contract pattern above); the previous image version runs normally against the expanded schema. If a bug in the new version corrupted data, stop the service (`sudo systemctl stop aegis`), perform a Point-in-Time Restore (PITR) of RDS to an instance prior to deployment, update the connection URL in Secrets Manager, and open an investigation issue:
   ```bash
   aws secretsmanager put-secret-value --secret-id aegis/<env>/AEGIS_DATABASE_URL \
     --secret-string "postgres://aegis:<password>@<new-rds-host>:5432/aegis?sslmode=require"
   ```
5. **Infrastructure Rollback:** Revert commits in `deploy/tofu`, merge to main, and run workflow with `action=apply`.

## 3. Secret Rotation

The server dynamically reloads all secrets every `refresh_s` (300 s), and re-reads failed secrets immediately upon receiving an authentication rejection (HTTP 401 from model APIs, invalid webhook signature). No server restart is required; ongoing requests preserve existing values. Store secret values via stdin to prevent recording secrets in shell history:

```bash
aws secretsmanager put-secret-value --secret-id aegis/<env>/<NAME> --secret-string file:///dev/stdin <<< "$VALUE"
```

| Secret | Rotation Procedure |
| --- | --- |
| `ANTHROPIC_API_KEY` | Generate new API key in Anthropic console $\rightarrow$ update Secret $\rightarrow$ wait 5 minutes (or first 401 retry) $\rightarrow$ revoke previous key |
| `AEGIS_DATABASE_URL` | Execute `ALTER ROLE aegis PASSWORD ...` (via SSM port-forwarding as in Step 0) $\rightarrow$ immediately update Secret URL. Existing connections stay alive; new connections use the new credentials. (To avoid connection blips, provision role `aegis2`, update secret URL, then drop old user) |
| `AEGIS_SESSION_KEY` ($\ge 32$ bytes, `openssl rand -hex 32`) | Set new random value. Active user sessions and open review forms expire; users re-authenticate via OIDC |
| `AEGIS_OIDC_CLIENT_SECRET` | Generate secondary client secret in SSO provider (keep both active) $\rightarrow$ update Secret in AWS $\rightarrow$ revoke old SSO secret |
| `AEGIS_GITHUB_WEBHOOK_SECRET`, `AEGIS_GITLAB_WEBHOOK_TOKEN` | Update value in Secrets Manager first, then update webhook settings in GitHub/GitLab. Requests arriving mid-transition re-trigger secret reload; webhooks can be redelivered from forge UI |
| `AEGIS_GITHUB_COMMENT_TOKEN`, `AEGIS_GITLAB_COMMENT_TOKEN`, repository tokens (`token_env` in repo settings) | Generate new token $\rightarrow$ update Secret in AWS $\rightarrow$ revoke previous token |

**Compromised Secrets:** Revoke compromised tokens at the issuing provider **first**, then provision new values. Check AWS CloudTrail logs for `GetSecretValue` callers. The RDS master password is automatically rotated by AWS RDS; the application does not consume it.

To register new repository tokens: add their names to `repo_secret_names` in `TOFU_TFVARS_<ENV>`, run `action=apply`, then write secret values.

### On-Premise File-Based Secrets (#261)

Configuration: `[secrets] source = "file"`, `dir = "/run/secrets"`. Each secret corresponds to a file named after the secret key: Docker secrets, Kubernetes Secrets mounted as volumes (`defaultMode: 0400`), or systemd credentials (`LoadCredential=`, where `dir` resolves to `$CREDENTIALS_DIRECTORY`).
- Whitespace and trailing newlines are trimmed upon reading.
- **Security Validation:** The server strictly rejects files readable or writable by group/others (enforces `0400` or `0600`) and symlinks resolving outside `dir`. Missing mandatory secrets halt server startup with an explicit error.
- **Atomic Rotation:** Update secret files by writing to a neighboring temporary file followed by an atomic `mv`, ensuring the process never reads partially written files:

  ```bash
  umask 077; printf '%s\n' "$VALUE" > /run/secrets/.NAME.new && mv /run/secrets/.NAME.new /run/secrets/NAME
  ```

## 4. Troubleshooting

Host access: `aws ssm start-session --target <instance_id>`. Logs: CloudWatch Logs `/aegis/<env>/server` (structured JSON; filter `{ $.level = "ERROR" }`), on host via `sudo journalctl -u aegis`. Service status: `systemctl status aegis`, `sudo docker ps`. Metrics and Grafana: see [5. Monitoring](#5-monitoring).

### Server Startup Failures

- Check `journalctl -u aegis -n 100`. Server terminates startup when required secrets are missing, printing the exact secret name: update secret (Section 3), then `sudo systemctl restart aegis`.
- `AccessDenied` reading secrets: verify secret ARN follows naming `aegis/<env>/<NAME>`; host IAM role is strictly scoped to this prefix.
- Image pull failures: check image presence in ECR (`aws ecr describe-images --repository-name aegis-server`) and verify lifecycle policy retention (keeps 30 latest images).
- `permission denied ... docker.sock` in job logs: verify `DOCKER_GID` in `/etc/aegis/aegis.env` matches `getent group docker`.

### Sustained LLM Provider Errors

Symptoms: elevated failure rates displaying provider responses (5xx, 429, timeout), jobs exhausting infrastructure retry limits (3 retries with exponential backoff starting at 30 s).

1. Check official provider status pages; for customer-jp, check AWS Bedrock status in `ap-northeast-1` (Service Health). Never migrate customer-jp to alternative regions: customer data residency is locked to Japan.
2. 401/403 errors: API key revoked or expired $\rightarrow$ rotate key (Section 3). Bedrock `AccessDenied`: model entitlement not enabled in AWS account, or missing `BedrockInJapan` IAM policy on host.
3. Sustained 429 Rate Limits: lower `max_workers` in tfvars server config (`apply`), or request quota increase.
4. Extended Outages: pause worker execution while keeping API, webhooks, and dashboard alive; incoming jobs safely buffer in PostgreSQL:

   ```bash
   sudo sed -i 's/--role all/--role api/' /etc/systemd/system/aegis.service
   sudo systemctl daemon-reload && sudo systemctl restart aegis
   # Once provider recovers: revert --role api -> --role all, daemon-reload, restart
   ```

5. Recovering interrupted jobs: retry failed jobs via `POST /api/v1/jobs/{id}/retry`.

### Queue Backlog Stalling

Symptoms: jobs remaining in `queued` state for prolonged durations (visible on Grafana dashboard or `GET /api/v1/jobs?status=queued`).

1. Worker status: verify logs contain `worker started`; inspect `sudo docker ps`. If no jobs are `running`, the worker crashed or is running with `--role api`.
2. Stalled `running` jobs: leases expire after `lease_s` (60 s), returning abandoned jobs to the queue. Stalled sandbox containers: inspect `sudo docker ps --filter name=aegis-gate`, remove with `sudo docker rm --force --volumes <name>`. The worker removes each gate container once it ends, not `--rm`, so it can first read whether the container ran out of memory (#320). If a worker died mid-step, stopped ones may remain: `sudo docker ps -aq --filter name=aegis-gate --filter status=exited | xargs -r sudo docker rm --volumes`. A step failing with "out of memory" hit `[run.sandbox_limits] memory_mb` (or the profile's `sandbox.memory_mb`): raise it, or lower `CARGO_BUILD_JOBS` and the like in `[run.sandbox_env]`.
3. Concurrency constraints: check host `max_workers` and repo-specific `repos.max_concurrent_jobs`. If one repo starves the queue: cancel excess tasks (`POST /api/v1/jobs/{id}/cancel`) and verify webhook delivery deduplication.
4. Host resource exhaustion: inspect `top`, `sudo docker stats`. Scale up `instance_type` (triggers instance replacement, Section 1) or decrease `max_workers`.
5. Workspace storage exhaustion: check `df -h /data`. Prune obsolete images via `sudo docker image prune -a --filter until=168h` (preserves active images), clean finished workspaces in `/srv/aegis/.workspace` (check active jobs via `GET /api/v1/jobs?status=running`), or expand EBS volume `workspace_volume_gb` (`apply`, then `sudo xfs_growfs /data`).

### Database Storage Exhaustion

Symptoms: write failures (`could not extend file`, `No space left`), RDS state `storage-full`, job dispatch failures.

1. RDS auto-scales storage up to `db_max_storage_gb` (default 200 GB). If ceiling is hit: increase `db_max_storage_gb` (or `db_allocated_storage_gb`) in tfvars and apply. (Note: RDS enforces a 6-hour cooling period between storage scale events).
2. Identify top space-consuming tables (via SSM port-forwarding as in Step 0, role `aegis`):

   ```sql
   SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) FROM pg_class
   WHERE relkind = 'r' ORDER BY pg_total_relation_size(oid) DESC LIMIT 10;
   ```

3. Never delete `audit_log` rows manually (append-only table protected by database triggers) or ledger entries (financial and KPI records). Data retention pruning requires formal retention policies.
4. `VACUUM` blocked by long-running transactions: query active locks via `SELECT pid, state, xact_start FROM pg_stat_activity ORDER BY xact_start;` and terminate blocking processes via `SELECT pg_terminate_backend(<pid>);`.

## 5. Monitoring

Every deployment provisions a dedicated monitoring EC2 instance within the same VPC and region (`deploy/tofu/modules/aegis/monitoring.tf`; can be disabled via `monitoring = { enabled = false }`). The monitoring host runs three systemd containers in `--network host` mode listening **strictly on 127.0.0.1**. Security groups expose no public inbound ports.

| Component | Specifications |
| --- | --- |
| Prometheus (`prometheus`) | Discovers the server via EC2 service discovery (`Name=aegis-<env>-server`) and scrapes `/metrics` on port 9464 every 30 s. The Aegis server listens on `0.0.0.0:9464`; host security group permits access solely from the monitoring instance; ALB does not route port 9464. Loads rules from `deploy/alerts/aegis.rules.yml`, retains metrics for `retention_days` (30 days) |
| Alertmanager (`alertmanager`) | Groups alerts by `alertname` and `repo`, publishes notifications to SNS topic `aegis-<env>-alerts` (output `alerts_topic_arn`), repeats notifications every 4 hours while firing |
| Grafana (`grafana`) | Preconfigured Prometheus datasource and dashboards loaded from `deploy/grafana/*.json` (folder `aegis`) |
| Configuration Sync | S3 bucket `aegis-<env>-monitoring-<account>` populated by OpenTofu. Timer `aegis-monitoring-sync` syncs files to `/etc/aegis-monitoring` every 5 minutes; automatically reloads Prometheus and Alertmanager upon changes |
| Persistent Data | Dedicated EBS volume mounted at `/data` (TSDB, silence state, Grafana SQLite DB): persists across instance replacement |

**Accessing Grafana** (from operator machine via SSM, identical to server access):

```bash
aws ssm start-session --target <monitoring_instance_id> \
  --document-name AWS-StartPortForwardingSession --parameters portNumber=3000,localPortNumber=3000
# Initial setup: retrieve generated admin password from instance
aws ssm start-session --target <monitoring_instance_id>   # then run: sudo cat /data/grafana-admin-password
```

Open http://localhost:3000, user `admin`. Prometheus (port 9090) and Alertmanager (port 9093) can be accessed using identical port-forwarding patterns.

**Subscribing to Alerts:** Add email addresses to `monitoring.alert_emails` in `TOFU_TFVARS_<ENV>`, run `action=apply`, and confirm the AWS SNS subscription email. External notification channels (Slack via AWS Chatbot, PagerDuty) subscribe directly to the SNS topic. For `customer-jp`, alert payloads include repository identifiers: ensure recipients are authorized to view those repositories.

**Modifying Alert Rules & Dashboards:** Edit `deploy/alerts/aegis.rules.yml` (tested via `aegis.rules.test.yml`, validated in CI with `promtool`) or `deploy/grafana/*.json`, merge, and run `action=apply`. The monitoring host syncs changes within 5 minutes without replacing instances. Changing monitoring image versions (`monitoring.*_version`) triggers instance replacement, while TSDB data on `/data` remains preserved.

| Alert | Severity | Action |
| --- | --- | --- |
| `AegisServerDown` | critical | [Server Startup Failures](#server-startup-failures); host down or port 9464 blocked |
| `AegisProviderErrorsSustained` | critical | [Sustained LLM Provider Errors](#sustained-llm-provider-errors) |
| `AegisQueueBacklog` | warning | [Queue Backlog Stalling](#queue-backlog-stalling) |
| `AegisCacheReadRatioLow` | warning | Prompt order altered or cache breakpoint misplaced: diff latest deployment, inspect per-repo cache rates on dashboard |

**Monitoring Host Triage:** Access via `aws ssm start-session --target <monitoring_instance_id>`, inspect services: `systemctl status prometheus alertmanager grafana aegis-monitoring-sync.timer` and `sudo journalctl -u aegis-monitoring-sync`. If the `aegis` target on Prometheus Targets page reports `down` while server is running: verify security group port 9464 rules and `[metrics] listen` configuration in `/etc/aegis/server.toml`.

## 6. Adding Repositories

Step-by-step onboarding of GitHub or GitLab repositories, from initial registration to automated PR generation. CLI commands reference: `sudo docker exec aegis aegis-server --config /etc/aegis/server.toml <command>`, abbreviated below as `... <command>`.

### Prerequisites

1. **Target PR Repository (`fork`).** The agent pushes branches named `agent/*` and submits PRs **into `fork.owner/fork.name`**, targeting its default branch. Two deployment models:
   - **Dedicated Bot Fork:** Maintainers merge PRs from the bot fork into the upstream repository. The bot requires zero write access to the upstream repo.
   - **Direct Upstream Repository (`fork` equals upstream repo):** PRs open directly in the upstream repo. The bot requires write access, scoped to `agent/*` branches via branch protection rules.

   The fork default branch must match the upstream default branch and be synchronized regularly. PRs open in draft status when `[run] draft_prs = true` (default).

2. **Fork Authentication Token** (`fork.token_env`, secret key name). Fine-grained Personal Access Token (PAT) for the bot account:
   - Target fork repository: *Contents* Read/Write, *Pull requests* Read/Write.
   - Upstream repository: *Issues* Read (to ingest issue details), *Actions* Read (to analyze CI run failures and logs, #250). For private repositories, grant *Contents* Read for cloning and fetching.

   Store token values as described in [Section 3](#3-secret-rotation); add new secret names to `repo_secret_names` first.

   **GitLab Forks (#252):** In `[settings.fork]`, specify `platform = "gitlab"` and configure `api` as the instance API root (`https://gitlab.com/api/v4` or self-hosted); `owner` is the namespace (including subgroups), `name` is the project slug. The agent pushes branches over HTTPS (token authenticated via user `oauth2`) and opens **merge requests** (draft when `draft_prs = true`). Token requires scopes `api` and `write_repository` (plus `read_repository` for private repos). GitLab issues (labeled `aegis`) and broken CI pipelines on the default branch (#253) trigger automated repair jobs. **Review rounds on MRs (#254):** Comments containing `/aegis fix` by project members with Developer role or higher trigger repair cycles on the agent's branch.

3. **Issue Comments:** Configured globally via `AEGIS_GITHUB_COMMENT_TOKEN` with *Issues* Write permission on upstream repositories. For GitLab, set `AEGIS_GITLAB_COMMENT_TOKEN`. For GitHub Enterprise or self-hosted GitLab, configure container environment variables `AEGIS_GITHUB_API` / `AEGIS_GITLAB_API`.

### Registration and Cloning

4. Create repository definition file, e.g. `typst.toml` (all keys in `[settings]` validate against `RepoSettings` in [registry.rs](../../crates/aegis-lifecycle/src/registry.rs); unrecognized keys are rejected):

   ```toml
   slug = "typst"                         # Identifier in paths, branches, dashboard
   url = "https://github.com/typst/typst" # Upstream repo URL matched against webhooks
   default_branch = "main"
   language = "rust"                      # python, rust, go, typescript, java, csharp
   mode = "poc"                           # or customer-jp
   max_concurrent_jobs = 1

   [settings]
   # Repository-specific conventions appended to system prompt after language profile
   ```

### RBAC and Budgets

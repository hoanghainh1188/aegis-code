# Operations Runbook: On-Premise Deployment

For operators running Aegis on self-hosted infrastructure without AWS ([ADR 0007](../adr/0007-on-premise-deployment.md), #262). For AWS cloud deployments, see [AWS Runbook](README.md).

> **First install?** Follow [Install Aegis on Premise](../install-on-premise.md): one path from a blank machine to the first PR, including how to make the bot, the tokens and the SSO client, with a check after each step. This runbook is the reference for operating it afterwards.

Core operations: [Installation & Setup](#1-installation--setup), [Registering Repositories](#2-registering-repositories), [Upgrades & Rollback](#3-upgrades--rollback), [Backup & Disaster Recovery](#4-backup--disaster-recovery). Two installation methods are supported; the recommended default is **Docker Compose**. The **systemd** method is detailed in [Section 5](#5-systemd-alternative-to-compose).

## Prerequisites

| Requirement | Specification |
| --- | --- |
| Host Machine | Linux x86_64 or arm64 (images are published for `linux/amd64` and `linux/arm64`; releases up to 0.5.0 have `linux/amd64` only, #405). Minimum: 4 vCPUs, 16 GB RAM, 100 GB SSD storage (sandbox images, git clones, and build caches reside locally). The machine should be dedicated exclusively to Aegis |
| Docker Engine | Docker Engine 25+ (API 1.44, the oldest `aegis-docker-proxy` passes) and Docker Compose plugin v2 |
| Outbound Network | Access to forges (GitHub, GitLab) and model APIs (Claude API, AWS Bedrock), unless utilizing local models. For isolated networks without Internet access, use the [offline bundle](../release.md#air-gapped--offline-environments) |
| Inbound Traffic | Port 8080 behind your TLS reverse proxy: dashboard, REST API, webhooks. Compose publishes it on all interfaces unless `AEGIS_PUBLISH` says otherwise ([Reverse Proxy](#reverse-proxy-configuration-tls-termination)) |

## Preparation Checklist

Collect these before installing; most of them come from other teams and take longer than the installation itself.

| # | What | Used for | Ends up in |
| --- | --- | --- | --- |
| 1 | A host matching the prerequisites above, with Docker running | Server, PostgreSQL, gate sandboxes | — |
| 2 | A DNS name and a TLS certificate for it, behind a reverse proxy (examples below) | Dashboard, REST API, webhooks | `public_url` in `server.toml` |
| 3 | An OIDC client in your SSO (Keycloak, Entra ID, Okta, …) with redirect URI `https://<public_url>/auth/callback` | Dashboard login | `[auth.oidc] issuer`, `client_id`; secret file `AEGIS_OIDC_CLIENT_SECRET` |
| 4 | A model: a Claude API key, AWS Bedrock access, or a local model server (Ollama / vLLM) | The agent | Secret file `ANTHROPIC_API_KEY`, or a mode file in `./modes` |
| 5 | A bot account on GitHub/GitLab, and for each repo the fork it opens PRs in | Branches `agent/*` and PRs | `[settings.fork]` of each repo |
| 6 | A token of the bot per repo (scopes: [Adding Repositories](repos.md#prerequisites), step 2) | Clone, push, open PRs, read CI logs | Secret file named by the repo's `token_env` |
| 7 | A token allowed to comment on upstream issues | Progress and results on the issue | Secret file `AEGIS_GITHUB_COMMENT_TOKEN` (GitLab: `AEGIS_GITLAB_COMMENT_TOKEN`) |
| 8 | Admin rights on each upstream repo, or someone who has them | Adding the webhook | — |
| 9 | The email of the first administrator (as your SSO reports it) | First `grant ... admin` | — |

The database password, session key and GitHub webhook secret are generated by `install.sh`.

> [!WARNING]
> **Privilege Boundary:** Controlling the Docker daemon grants effective root privileges on the host machine. Only the `docker-proxy` service (`aegis-docker-proxy.service` under systemd) mounts `/var/run/docker.sock`. The `aegis` container reaches the daemon through the proxy's socket, which passes only the gate's calls and hardened sandboxes with the workspace mounted ([ADR 0010](../adr/0010-docker-socket-proxy.md), [AWS Runbook](README.md#worker-and-docker-isolation), "Worker and Docker Isolation"). With Sonar enabled in a mode, add `--network <[sonar] network>` and `--writable-image <[sonar] image>` to the proxy's `command` in `docker-compose.yml` (systemd: `AEGIS_DOCKER_PROXY_ARGS` in `/etc/aegis/aegis.env`).

## 1. Installation & Setup

Execute from a clean repository checkout pinned to your target release tag (`git checkout vX.Y.Z`), located in `deploy/compose/`:

1. **Host Preparation (One-Time Execution):**

   ```bash
   sudo ./install.sh
   ```

   The script is idempotent and never overwrites existing configurations. It provisions:
   - `/srv/aegis/.workspace`, owned by container uid `10001:10001`;
   - `./secrets/` directory containing randomly generated database credentials, session key, and GitHub webhook secret;
   - `.env` file populated with host Docker socket GID and default sandbox profile image lists;
   - Initial `server.toml` (copied from `server.toml.example`).

   On a terminal it then asks for the site's values still unset (#476): `public_url`, the OIDC issuer and client ID, the first admin's email, the sandboxes to pull, and the secrets `ANTHROPIC_API_KEY`, `AEGIS_OIDC_CLIENT_SECRET` and `AEGIS_GITHUB_COMMENT_TOKEN`. Secrets are read without echo and written as described in step 3. An empty answer skips a value; running the script again asks for what is still missing. For an unattended install, give the values in the environment instead (`sudo -E` keeps it) with `AEGIS_NONINTERACTIVE=1`. The variables are `AEGIS_PUBLIC_URL`, `AEGIS_OIDC_ISSUER`, `AEGIS_OIDC_CLIENT_ID`, `AEGIS_ADMIN_EMAIL`, `AEGIS_SANDBOXES`, and each secret by its name. An invalid value then stops the script.

   ```bash
   sudo -E AEGIS_NONINTERACTIVE=1 AEGIS_PUBLIC_URL=https://aegis.example.com \
     AEGIS_ADMIN_EMAIL=admin@example.com ./install.sh
   ```

   Steps 2 and 3 are left for what you skipped and for `[modes]`.

2. **Configure `server.toml`** for what step 1 did not set: `public_url` and `[auth.oidc]` as in the [install guide, B4](../install-on-premise.md#b4-servertoml). `[modes]` names the configuration of each mode. For a local model (Ollama / vLLM), create `./modes/local.toml` from [config/local.toml](../../config/local.toml) and set `poc = "/etc/aegis/modes/local.toml"`.

3. **Populate Secrets** that step 1 did not write: one file each in `./secrets/`, readable only by its owner and owned by uid `10001:10001`, as in the [install guide, B5](../install-on-premise.md#b5-secrets). They are `ANTHROPIC_API_KEY` (not needed with a local model), `AEGIS_OIDC_CLIENT_SECRET`, `AEGIS_GITHUB_COMMENT_TOKEN`, and each repo's fork token. Rotation: [Secret Rotation](README.md#3-secret-rotation).

4. **Deploy Application Version:**

   ```bash
   sudo ./aegis-deploy.sh X.Y.Z             # Pull images from GHCR
   sudo ./aegis-deploy.sh --offline X.Y.Z   # Deploy using preloaded offline bundle
   ```

   The deployment script pulls server and sandbox images (or verifies pre-loaded offline images), tags sandboxes with bare names expected by profiles, updates `AEGIS_VERSION` in `.env`, triggers `docker compose up`, and polls healthcheck endpoints until healthy. Database migrations run automatically during startup.

   The version is written without `v` (`0.1.0`, not `v0.1.0`): it is the image tag, while the git tag is `v0.1.0`.

   #### Images Built from Source

   To run a commit that is not a release (or without access to GHCR), build the images from the checkout under the names `aegis-deploy.sh` expects, then deploy them as an offline version. The sandbox list is `AEGIS_SANDBOXES` in `.env`; `python` is always needed (it is also the egress proxy of the gate's fetch step):

   ```bash
   version=0.1.0-local
   registry=ghcr.io/hoanghainh1188     # AEGIS_REGISTRY in .env
   (cd ../.. && docker build -t "$registry/aegis-server:$version" -f docker/server/Dockerfile .)
   for p in python go rust node java dotnet; do
     docker build -t "$registry/aegis-sandbox-$p:$version" "../../docker/$p"
   done
   sudo ./aegis-deploy.sh --offline "$version"
   ```

   Building all images takes a while (the server image compiles the workspace). Build only the sandboxes of your repos' languages, and shorten `AEGIS_SANDBOXES` in `.env` to match.

5. **Post-Installation Verification:**
   - Verify health: `curl http://127.0.0.1:8080/api/v1/health`
   - Access dashboard at your configured domain and log in via OIDC.
   - Grant initial administrator privileges. `aegis-deploy.sh` does this itself for `AEGIS_ADMIN_EMAIL` in `.env`, before that person's first sign-in. That works only if the SSO marks the email verified (not Entra ID, [install guide A4](../install-on-premise.md#a4-an-oidc-client-in-your-sso)). Otherwise, leave `AEGIS_ADMIN_EMAIL` unset, sign in once, then:

   ```bash
   docker compose exec aegis aegis-server --config /etc/aegis/server.toml grant admin@example.com admin
   ```

### Reverse Proxy Configuration (TLS Termination)

By default Docker Compose publishes port 8080 on **all interfaces** (`0.0.0.0:8080`), so plain HTTP is reachable from the network next to your proxy. When the proxy runs on the same host, keep the port on loopback by adding this line to `.env` and re-running `aegis-deploy.sh` (or `docker compose up -d`):

```bash
AEGIS_PUBLISH=127.0.0.1:8080
```

Check with `docker compose port aegis 8080`, which should print `127.0.0.1:8080`. Then configure a reverse proxy with TLS termination to forward requests:

#### Nginx Example
```nginx
server {
    listen 443 ssl http2;
    server_name aegis.internal.example.com;

    ssl_certificate     /etc/ssl/certs/aegis.crt;
    ssl_certificate_key /etc/ssl/private/aegis.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

#### Caddy Example
```caddy
aegis.internal.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Prometheus metrics listen locally at `127.0.0.1:9464/metrics`. Standard alerting rules can be adopted from [deploy/alerts/](../../deploy/alerts/).

## 2. Registering Repositories

### Before Registering: `aegis check-repo`

The server image ships `aegis check-repo` (#450, #474), so no Rust toolchain is needed on the host. It runs in the `aegis` container and reaches the daemon through `docker-proxy`, as jobs do: the same uid, the same workspace mounts, the same sandbox images. It checks the profile, the lockfile, the daemon and the profile's sandbox image, the fetch hosts, and runs the root gate (format, lint, tests) in a `--network none` sandbox. Run it before `add-repo.sh`; every blocking item must pass.

Tests must pass on the base branch (#487): a test that fails there blocks, even though the gate lets a patch through when the base fails the same tests. Format or lint that fails on the base is a warning: the gate judges patches by the findings they add.

From `deploy/compose/`, with the server healthy:

1. Clone the repo into the workspace, owned by uid 10001 (for a private repo, clone with a token that can read it):

   ```bash
   sudo git clone --branch main https://github.com/<owner>/<name> /srv/aegis/.workspace/preflight/myrepo
   sudo chown -R 10001:10001 /srv/aegis/.workspace/preflight/myrepo
   ```

2. Write a configuration from the mode's (`poc` or `customer-jp`), without its `[repo]` tables, and add the repo. The fork is not used by the check, but the configuration needs one:

   ```bash
   docker compose exec -T aegis sed '/^\[repo/,/^\[identity\]/{/^\[identity\]/!d}' config/poc.toml > myrepo-check.toml
   cat >> myrepo-check.toml <<'EOF'

   [repo]
   path = ".workspace/preflight/myrepo"
   language = "python"
   base = "main"
   key = "myrepo"

   [repo.fork]
   owner = "<bot>"
   name = "<name>"
   token_env = "UNUSED"
   EOF
   sudo install -D -o 10001 -g 10001 myrepo-check.toml /srv/aegis/.workspace/preflight/myrepo.toml
   ```

   Paths are relative to `/srv/aegis` in the container. A monorepo adds its `[[repo.dirs]]` ([ADR 0004](../adr/0004-multi-language-profiles.md)); a repo with its own commands adds `[repo.overrides]`, as `config/poc.toml` does for scrapy.

3. Run the check:

   ```bash
   docker compose exec aegis aegis check-repo --config .workspace/preflight/myrepo.toml
   ```

   The command exits non-zero when an item blocks. `--skip-tests` leaves out the baseline gate. Remove `/srv/aegis/.workspace/preflight/myrepo*` afterwards: `add-repo.sh` clones the repo again.

### Registering

From `deploy/compose/`, with the server healthy, `sudo ./add-repo.sh` registers a GitHub repo (#476):
- it asks for the upstream URL, slug, default branch, language, mode, the fork, and the fork's token (read without echo);
- it asks for the maintainers' and reviewers' emails, and the monthly budget;
- it writes the token and the repo file, runs `repo add` and `grant`, and prints the webhook settings with the link to the repo's budget page.

Every value can come from the environment instead, as for `install.sh`. The variables are `AEGIS_REPO_URL`, `AEGIS_REPO_SLUG`, `AEGIS_REPO_BRANCH`, `AEGIS_REPO_LANGUAGE`, `AEGIS_REPO_MODE`, `AEGIS_FORK_OWNER`, `AEGIS_FORK_NAME`, `AEGIS_FORK_TOKEN`, `AEGIS_MAINTAINERS`, `AEGIS_REVIEWERS` and `AEGIS_MONTHLY_USD`. The script is for GitHub repos; a GitLab repo is registered by hand. Its grants, like any made before someone's first sign-in, need an email the SSO marks verified.

By hand, the steps are those of [Adding Repositories](repos.md), with these on-premise specifics, from `deploy/compose/`:

- **Server commands:** `docker compose exec aegis aegis-server --config /etc/aegis/server.toml <command>`.
- **Fork token:** a file `./secrets/<token_env>`, owner-only and owned by uid 10001. The server reads new secret files within `[secrets] refresh_s` (5 minutes); no restart is needed.

  ```bash
  sudo sh -c 'umask 077; printf "%s\n" "$TOKEN" > secrets/AEGIS_TOKEN_MYREPO; chown 10001:10001 secrets/AEGIS_TOKEN_MYREPO'
  ```

- **Repo file:** in the workspace, so the container can read it:

  ```bash
  sudo install -D -o 10001 -g 10001 myrepo.toml /srv/aegis/.workspace/repo-files/myrepo.toml
  ```

- **Webhooks:** payload URL `https://<public_url>/webhooks/github`, secret from `sudo cat secrets/AEGIS_GITHUB_WEBHOOK_SECRET`.

## 3. Upgrades & Rollback

1. Read CHANGELOG for breaking changes and review schema modifications against [Expand/Contract Guidelines](README.md#database-migrations-expandcontract-pattern).
2. Create an immediate database backup ([Section 4](#4-backup--disaster-recovery)).
3. Switch git tracking to the target version (`git checkout vX.Y.Z`; existing configuration in `server.toml`, `.env`, and `./secrets/` is untouched), then run:
   ```bash
   sudo ./aegis-deploy.sh X.Y.Z
   ```
   Active jobs are permitted up to `drain_s` (10 minutes) to complete before previous containers shut down.
4. **Rollback:**
   ```bash
   sudo ./aegis-deploy.sh <previous-version>
   ```
   The database schema is not rolled back; older versions safely execute on schemas migrated by newer releases. If a bug corrupted data, restore PostgreSQL from the backup taken in Step 2.

## 4. Backup & Disaster Recovery

```bash
sudo ./backup.sh /backup              # Database snapshot: aegis-db-<timestamp>.dump (pg_dump -Fc)
sudo ./backup.sh /backup --workspace  # Adds .workspace/state (git clones, AST indexes, module maps)
```

Schedule backups daily via cron or systemd timer. Store generated dumps, `./server.toml`, and `./secrets/` in an offsite vault.

### Disaster Recovery / Host Migration

```bash
# On new host:
sudo ./install.sh                     # Restores directory structure; restore server.toml and secrets/
docker compose up --detach --wait postgres
docker compose exec -T postgres pg_restore -U aegis -d aegis --clean --if-exists < /backup/aegis-db-<timestamp>.dump
sudo tar -C /srv/aegis -xzf /backup/aegis-workspace-<timestamp>.tar.gz   # Optional workspace cache
sudo chown -R 10001:10001 /srv/aegis/.workspace                         # Ensure uid 10001 ownership
sudo ./aegis-deploy.sh <current-version>
```

If workspace cache is omitted, workers will automatically re-clone repositories and regenerate module maps prior to executing jobs.

## 5. systemd Alternative to Compose

For environments with an existing PostgreSQL instance wishing to manage Aegis via systemd services. The systemd unit [deploy/systemd/aegis.service](../../deploy/systemd/aegis.service) is identical to the unit deployed on AWS:

```bash
sudo deploy/systemd/install.sh   # Sets up /etc/aegis, /srv/aegis/.workspace, unit, /usr/local/bin/aegis-deploy
```

- Configure `/etc/aegis/server.toml` with `[metrics] listen = "127.0.0.1:9464"` (the unit runs with `--network host`).
- Store database connection string in `/etc/aegis/secrets/AEGIS_DATABASE_URL`.
- Host-specific parameters are maintained in `/etc/aegis/aegis.env`: `AEGIS_RUN_ARGS` (network, mounts), `AEGIS_SANDBOXES`.
- Deploy or rollback using `sudo aegis-deploy X.Y.Z` (or `--offline X.Y.Z`). Inspect service logs via `journalctl -u aegis`.

## Troubleshooting Guide

| Issue | Remediation |
| --- | --- |
| `aegis-deploy.sh: ... is not healthy` | Inspect `docker compose logs aegis`. The server halts startup if required secrets are missing, printing the missing secret name |
| `secret ... is open to others than its owner` | Run `chmod 0400 secrets/<NAME>` and `chown 10001:10001 secrets/<NAME>` |
| `permission denied ... docker.sock` in `docker-proxy` logs | Verify `DOCKER_GID` in `.env` (or `/etc/aegis/aegis.env` for systemd) matches host group of `/var/run/docker.sock` |
| `aegis-docker-proxy refused the call: …` in job logs | The proxy blocked a Docker call outside its policy. `docker compose logs docker-proxy` (systemd: `docker logs aegis-docker-proxy`) shows each `refused` line with its reason. For Sonar, see the Privilege Boundary note in Section 1 |
| Gate fails with `No such image: aegis-sandbox-...` | Required language sandbox image is missing from `AEGIS_SANDBOXES` or not loaded. Note: the `fetch` step always requires `aegis-sandbox-python` (egress proxy) |
| Job halted with `API root ... must use https` | Forge API roots (`fork.api`, `AEGIS_GITHUB_API`) must utilize `https://`. Insecure `http://` is allowed strictly for loopback test environments |
| `aegis` CLI reports `not_found` with service token | Service tokens require RBAC roles: `... grant <token-name> maintainer` |
| `repo add` fails with `could not read Username for 'https://github.com'` | GitHub rejected the fork token (wrong value, expired, or no *Contents* read on the repo); the token is sent on every clone, public repos included. Fix the file `./secrets/<token_env>` and run `repo add` again |
| Job mount error on `/work` | `/srv/aegis/.workspace` must exist on host matching container path, owned by uid 10001 |
